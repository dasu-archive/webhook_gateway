3 게이트웨이 판정

응답 코드는 전부 하나의 질문으로 결정된다. "제공자가 다시 보내게 할 것인가."

수신 판정 — 위에서부터 순서대로
검사실패 시왜 그 코드인가
slug 조회 · enabled404없는 주소다. 다시 보내도 없다

바디를 byte[] 로 받는 이유는 재직렬화하면 HMAC 이 원천적으로 깨지기 때문이다. DB 쓰기는 이 경로에 정확히 한 번뿐이다.

전달 판정에서 408 과 429 만 4xx 중 예외다. "지금은 안 된다"는 뜻이라 재시도가 유효하다. 이 둘을 DEAD 로 보내면 소비자가 스로틀링을 켜기만 해도 이벤트를 잃는다.

boolean permanent = status >= 400 && status < 500 && status != 408 && status != 429;

4 소비자 로직 — 이번에 새로 만든 것

중복일 때 예외를 던지지 않는 것이 핵심이다

중복에 무엇을 돌려주면게이트웨이가 하는 일
4xx데드레터로 보낸다 — 정상 처리한 건이 DEAD 가 된다
5xxmax_attempts 까지 계속 때린다
200재시도가 멈춘다 ✅

기록과 결제가 한 트랜잭션인 것도 핵심이다. @Transactional 이 없으면 결제가 실패해도 처리 기록만 남고, 재시도가 그 기록에 걸려 중복으로 스킵되면서 결제가 영영 유실된다.

이 성질 덕분에 잔액 부족이나 없는 주문은 롤백되어 processed_event 에 아무것도 남지 않는다. 나중에 충전하고 재생하면 다시 처리할 수 있다 — 실측으로 확인했다.

응답 코드는 게이트웨이에 대한 지시다

기준은 하나다. "똑같은 요청을 다시 보내면 성공할 가능성이 있는가."

헤더값소비자가 쓰는가

X-Gateway-Replay재생 이벤트인가 (현재 항상 false)안 쓴다

원본 헤더는 화이트리스트가 아니라 최소 블록리스트로 거른다. hop-by-hop, Host/Content-Length, 자격 증명, X-Gateway-* 만 뺀다. 화이트리스트를 못 쓰는 이유는 무엇이 서명 헤더인지 제공자마다 다르고 미리 다 알 수 없기 때문이다.

전제가 깨져 있다

이 PASSTHROUGH 설계는 소비자가 원 제공자의 서명을 재검증한다는 전제 위에 서 있다. 지금 소비자는 그 검증을 하지 않는다 — Part III 1절.

6 중복이 걸러지는 3개 지점

게이트웨이는 exactly-once 를 제공하지 않는다. 분산 트랜잭션 없이는 불가능하고, at-least-once + 소비자 멱등성이 유일한 실용적 해법이다. 3단은 선택이 아니라 필수다.

7 이번에 정한 결정

잔액 부족을 422 로 둔다 — 갈릴 수 있는 판단

충전을 기대해 5xx 로 재시도를 받는 선택도 가능하다. 그러나 게이트웨이 백오프의 상한이 1시간이라 충전을 기다리기엔 짧고, 그동안 워커 하나를 붙잡는다. 결제 실패는 인프라 재시도가 아니라 사용자에게 알려 해결할 일이라고 보고 4xx 를 택했다.

차감 금액은 페이로드가 아니라 DB 에서 읽는다

PaymentEvent.amount 는 받기만 하고 쓰지 않는다. account.withdraw(order.getAmount()) 다. 웹훅 바디는 외부에서 온 값이라 금액의 출처가 되면 안 된다. 서명이 유효해도 마찬가지다 — 서명은 "제공자가 보냈다"를 증명할 뿐 "금액이 맞다"를 증명하지 않는다.

이벤트 ID 헤더가 없으면 받지 않는다

중복 제거를 할 수 없는 요청을 받아 처리하면 결제가 몇 번 일어날지 아무도 모른다. 받아서 잘못 처리하는 것보다 거부하고 데드레터에 남기는 편이 낫다.

MySQL 은 한 인스턴스, 스키마만 나눈다

두 서비스가 논리적으로 완전히 분리되어 있다 — FK 도 조인도 없다. 인스턴스를 나누면 검증 환경만 무거워진다. 배포에서 갈라야 한다면 커넥션 문자열만 바꾸면 된다.

3 재시도 곡선 — 가장 많은 것을 알려준 시나리오

여기서 나온 문제

8번째 시도에서 성공했다. 한 번만 더 실패했으면 DEAD 였다.

8회로 커버되는 시간값
지터 없음 (NONE) — 1+2+4+8+16+32+64127초
FULL 지터 기댓값 — 각 구간이 random(0, base)63.5초
실측61.1초

FULL 지터는 thundering herd 를 막는 대신 같은 시도 횟수로 커버할 수 있는 다운타임을 절반으로 줄인다. 백오프 상한이 1시간이어도 근처에 가보지 못하고 소진된다.

즉 지금 설정은 소비자가 1분 넘게 다운되면 이벤트가 데드레터로 간다. 게이트웨이를 만든 이유가 "소비자 사정이 잠깐 나쁠 때 대신 붙들고 있는 것"인데, 그 '잠깐'이 1분이라는 뜻이다. 배포 한 번에 이벤트가 다 죽는다.

부수 관찰

  • duration_ms 가 시도마다 갈린다: 3,746 / 2 / 2 / 1 / 3 / 3,725 / 3,729ms. 즉시 커넥션 거부(1~3ms)와 연결 타임아웃(≈3.7초, connect-timeout: 3s)이 섞였다. 컨테이너 정지 직후 도커 네트워크 상태에 따라 갈리는 것으로 보이는데 단정할 수 없다. 중요한 것은 타임아웃이 걸린 시도가 그만큼 워커를 붙잡는다는 점이다.
  • event.last_backoff_ms 는 컬럼이 하나라 시도별 백오프 이력이 남지 않는다. 위 간격은 전부 delivery_attempt.started_at 차이로 역산한 값이다.

Part III

남은 과제

1차에서 이월된 것과 이번에 새로 드러난 것이 섞여 있다.

1 우선순위

  1. 1소비자 8081 을 비공개로한 줄이고, 지금 가장 큰 구멍을 절반 막는다
  2. 1b재시도 예산 재설정설정 한 줄. 지금 1분 다운에 이벤트를 잃는다
  3. 2소비자 서명 검증 또는 resign신뢰 경계를 세운다. 구멍의 나머지 절반
  4. 3시크릿 암호화2번에서 resign 을 택하면 선행 조건이 된다
  5. 4멱등키 정리 배치 — 게이트웨이 + 소비자안 하면 시간이 지날수록 반드시 나빠진다
  6. 5부하 측정설계가 "미측정"으로 남긴 판단들이 여기서 확정된다
  7. 6서킷 브레이커 · 재생5번의 결과가 임계값을 정해준다

가장 먼저 할 것은 1번과 1b 다. 둘 다 설정 한 줄인데, 하나는 서명 없이 결제되는 경로를 좁히고 하나는 1분 다운에 이벤트를 잃는 것을 막는다. 기능을 만들기 전에 이미 벌어져 있는 것부터 닫는 것이 순서다.

2 이번에 새로 드러난 것

2.1 소비자가 서명을 검증하지 않는다 — 가장 큰 구멍

002_WebhookService 어디에도 HMAC·서명·시크릿 관련 코드가 없다. X-Gateway-Event-Id 헤더와 orderId 만 있으면 누구의 요청이든 결제한다. compose 가 8081 을 호스트에 노출하는 것이 이 구멍을 실제로 도달 가능하게 만든다.

선택지내용비용
C. 포트 비공개compose 에서 8081 을 expose 로만 두고 ports 를 뺀다한 줄 · 지금 당장
A. 소비자가 원 서명 재검증X-Hub-Signature-256 을 자기 시크릿으로 검증소비자에 시크릿 관리가 생긴다
B. 게이트웨이가 재서명 (resign)소비자는 게이트웨이만 믿는다재생과 한 묶음. 시크릿 암호화가 선행

C 는 방어가 아니라 노출 축소다. 그것만으로 끝내면 안 된다 — 같은 네트워크 안이면 여전히 아무나 부를 수 있다. B 를 택하면 신뢰 경계가 이동한다. 소비자는 이제 GitHub 을 믿는 것이 아니라 게이트웨이를 믿는다.

2.2 소비자 중복 방어가 DB 격리 수준에 의존한다

ProcessedEvent 는 @Id 가 애플리케이션이 채우는 String 이다. Spring Data JPA 의 save() 는 isNew()(= id 가 null 인가)로 분기하므로 persist 가 아니라 merge 로 돈다 — SELECT 한 번 후 INSERT 또는 UPDATE.

REPEATABLE READ (MySQL 기본값) — 안전
  tx1: existsById 없음 → merge → INSERT
  tx2: existsById 없음 → merge → SELECT 없음(스냅샷) → INSERT → duplicate key
       → 롤백 → 500 → 게이트웨이 재시도 → existsById 에 걸림 → 200
  결과: 결제 1회

READ COMMITTED — 깨진다
  tx2: merge 의 SELECT 가 방금 커밋된 행을 본다 → UPDATE → 성공
       → processPayment 그대로 실행 → 중복 결제

지금 당장 문제는 아니지만 안전성의 근거가 코드가 아니라 DB 설정에 있다. Persistable<String> 을 구현해 isNew() 를 true 로 고정하거나 네이티브 INSERT 로 바꾸면 격리 수준과 무관해진다.

확인 필요

코드를 읽고 추론한 것이다. 동시 요청으로 이 경로를 실제로 밟아보지 않았다. 고치기 전에 재현 테스트부터 쓰는 것이 순서다.

2.3 재시도 예산이 1분짜리다

Part II 3절에서 나온 것이다. 해야 할 것은 셋 중 하나가 아니라 조합이다.

방법효과대가
max_attempts → 12~15커버 시간이 지수적으로 는다데드레터 진입이 늦어진다
jitter: DECORRELATEDrandom(initial, prev×3) 이라 평균 대기가 더 길다복구 곡선이 달라진다 — 비교 측정 필요
backoff.max → 5m후반 시도가 촘촘해진다소비자 압력이 는다

어느 조합이 맞는지는 지터 3종 복구 곡선을 비교해야 정해진다. 다만 지금 값이 명백히 짧다는 것은 이미 실측으로 나왔으므로, 측정 전이라도 max_attempts 를 올려두는 편이 낫다.

2.4 X-Gateway-Event-Id 가 게이트웨이 auto_increment 다

게이트웨이 DB 를 초기화하면(docker compose down -v) id 가 1부터 다시 시작하는데, 소비자의 processed_event 가 남아 있으면 새 이벤트가 중복으로 오인되어 조용히 스킵된다. 로그는 debug 라 보이지도 않는다. tools/e2e.sh 가 매번 DELETE FROM processed_event 를 하는 것이 사실상 이 문제의 우회다. 게이트웨이가 UUID 를 함께 발급하면 사라진다.

2.5 시도별 백오프 이력이 남지 않는다

event.last_backoff_ms 는 컬럼이 하나라 항상 마지막 값만 있다. 지터 3종을 비교하려면(2.3) 시도별 대기 시간이 그대로 남아야 한다. delivery_attempt 에 backoff_ms 컬럼을 추가하는 것이 맞다.

2.6 소비자에도 정리 배치가 없다

processed_event 는 무한히 쌓인다. 게이트웨이의 멱등키 정리 배치와 같은 문제인데, 보관 기간의 근거가 다르다.

보관 기간의 근거
게이트웨이 event제공자의 재시도 윈도우
소비자 processed_event게이트웨이의 재시도 윈도우 = max_attempts × 백오프 상한

2.3 에서 max_attempts 를 올리면 이 값도 같이 늘어야 한다. 짧게 잡으면 아직 재시도 중인 이벤트의 기록이 지워져 중복 결제가 난다.
