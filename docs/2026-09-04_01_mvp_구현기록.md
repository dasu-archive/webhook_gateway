## 1. 이번에 만든 것

설계 문서 12.1의 v1 범위에서 **뼈대에 해당하는 부분**을 구현했다.
웹훅 한 건이 제공자에서 소비자까지 도달하고, 실패하면 재시도되고, 소진하면 데드레터로 떨어지는
경로가 끝까지 이어진다.

```
제공자 ──POST──▶ 게이트웨이 ──POST──▶ 소비자
                 수신부 → 원장 → 전달부
                 (즉시 200)  (MySQL)  (재시도 + 데드레터)
```

| | 규모 |
| --- | --- |
| 프로덕션 코드 | 30파일 1,931줄 |
| 테스트 코드 | 5파일 785줄 |
| 검증 도구 | 목 소비자, 발신 스크립트 |

기술 스택은 설계 기준 그대로다. Spring Boot 3.5 / Java 21 / MySQL 8.0 / Flyway.
ORM 은 쓰지 않고 `JdbcClient` 로 직접 쓴다. 원장이 다루는 것은 **바이트와 잠금**이지 객체가 아니고,
`FOR UPDATE SKIP LOCKED` 를 JPA 로 감싸면 무엇이 잠기는지 보이지 않게 된다.

## 2. 결과물 구조

설계 5.1이 말한 대로 **박스는 하나**다. 아래 패키지는 하나의 Spring Boot 프로세스 안의 논리 구획이다.

| 패키지 | 파일 | 역할 | 설계 절 |
| --- | --- | --- | --- |
| `receive` | 10 | 원본 바이트 수신, 서명 검증, 멱등키 결정, 즉시 응답 | 6, 7.3 |
| `ledger` | 9 | 3테이블 도메인과 저장소. 클레임·상태 전이·좀비 회수 SQL | 7 |
| `dispatch` | 6 | 폴링 워커, 전달, 백오프/지터, 데드레터, 좀비 회수 배치 | 8, 10.1 |
| `admin` | 3 | 엔드포인트 등록·시크릿 교체·원장 조회 | 5 |
| `common` | 2 | 설정 프로퍼티, 헤더 정책 | — |

### 주요 타입

| 타입 | 무엇인가 |
| --- | --- |
| `WebhookReceiveController` | 수신부 전체. 컨트롤러 하나가 맞다 |
| `SignatureVerifier` | 제공자별 형식 차이를 흡수하는 전략. `github`, `standard` 2종 구현 |
| `EventRepository#claimBatch` | `SELECT ... FOR UPDATE SKIP LOCKED` → `UPDATE ... DELIVERING` |
| `EventDispatcher` | 한 건 전달과 결과 판정. 여기에 8.1.1의 판정 규칙이 있다 |
| `BackoffCalculator` | 지수 백오프 + 지터 3종 |
| `ZombieReclaimer` | 1분 주기 회수 배치 |

## 3. 요청 하나가 실제로 어떻게 흐르는가

설계 5.2의 흐름을 코드 레벨로 옮기면 이렇다.

### 수신 (목표 p99 50ms)

```
POST /webhooks/gh-push
  │
  ├─ WebhookReceiveController      @RequestBody byte[] 로 받는다
  │                                DTO 로 받으면 이 지점에서 이미 원본이 사라진다
  ├─ ReceiveService
  │   ├─ endpoint 조회             없거나 꺼져 있으면 404
  │   ├─ 크기 검사                  1MB 초과면 413
  │   ├─ SignatureVerifier.verify  현 시크릿 → 구 시크릿 순으로 시도
  │   │                            상수 시간 비교. 실패하면 401 (재시도 유발 안 함)
  │   ├─ 멱등키 결정                제공자 ID 있으면 PROVIDER_ID, 없으면 BODY_HASH
  │   └─ EventRepository.insert    유니크 인덱스 위반 → 200 duplicate
  │
  └─ 200 { "status": "accepted", "eventId": 1 }
```

**DB 쓰기는 정확히 한 번이다.** 설계 13절의 "수신부가 DB 에 묶임" 악순환을 피하려면
이 경로에 다른 것이 붙으면 안 된다.

### 전달

```
DispatchWorker (@Scheduled fixedDelay 500ms)
  │
  ├─ claimBatch(50)                별도 트랜잭션. id 만 집는다 (페이로드를 안 읽어야 짧다)
  │                                status=DELIVERING, attempt_count += 1
  ├─ 워커 스레드 8개로 분배
  │   └─ EventDispatcher.dispatch
  │        ├─ 원본 헤더 + X-Gateway-* 헤더로 POST
  │        ├─ 2xx        → DELIVERED
  │        ├─ 4xx        → DEAD (408/429 제외)
  │        └─ 5xx/예외   → attempt_count >= max ? DEAD : PENDING + 백오프
  │
  └─ 배치 전체가 끝나야 다음 폴링   인플라이트를 batch-size 로 묶어둔다

ZombieReclaimer (@Scheduled fixedDelay 1m)
  └─ DELIVERING 인데 updated_at 이 5분 지난 행 → PENDING
```

## 4. 설계 문서와 다르게 구현한 것

### 4.1 408/429 는 재시도한다

설계 8.1.1의 판정 규칙은 `4xx → 즉시 DEAD` 다. 근거는 "재시도해도 결과가 같다"는 것이고
대부분의 4xx 에 대해 맞다. 그러나 **408(Request Timeout)과 429(Too Many Requests)는 다르다.**

| | 뜻 | 재시도 효과 |
| --- | --- | --- |
| 400, 404, 422 | 이 요청은 영원히 처리할 수 없다 | 없다 |
| **408, 429** | **지금은 안 된다** | **있다** |

429 를 DEAD 로 보내면 소비자가 스로틀링을 켜기만 해도 이벤트를 잃는다. 게이트웨이를 만든 이유가
"소비자 사정이 잠깐 나쁠 때 대신 붙들고 있는 것"인데 그 상황에서 버리는 셈이다.
설계 8.1.1이 열거한 실패 유형 표에서 429 는 "소비자가 느림" 줄에 해당하고, 그 줄의 재시도 효과는
문서 자신이 **있다**고 적고 있다.

`EventDispatcher.handleResponse` 에 주석으로 남겼다.

```java
boolean permanent = status >= 400 && status < 500 && status != 408 && status != 429;
```

### 4.2 두 번째 제공자로 Stripe 대신 Standard Webhooks 를 골랐다

설계 6.3은 GitHub 과 Stripe 를 예로 든다. Stripe 대신 **Standard Webhooks** 스펙을 구현했다.

| | 이유 |
| --- | --- |
| 형식적으로 동등하다 | 둘 다 `{id}.{timestamp}.{body}` 를 서명 대상으로 삼는 타임스탬프 포함형이다 |
| 검증 가능하다 | 공개 스펙이라 발신 스크립트로 정확히 재현할 수 있다. Stripe 는 실계정이 필요하다 |
| 대비가 살아난다 | GitHub 은 타임스탬프가 없고 이쪽은 있다. 6.2의 세 논점 중 하나가 제공자마다 성립/불성립이라는 것이 드러난다 |

제공자를 늘리는 비용은 `SignatureVerifier` 구현 하나다. Stripe 가 필요해지면 그때 붙이면 된다.

## 5. 설계 문서에 없던 결정

구현하면서 정해야 했던 것들이다. 설계 문서가 다루지 않았거나, 스키마에 빠져 있던 부분이다.

### 5.1 스키마에 추가한 컬럼

| 컬럼 | 왜 필요했나 |
| --- | --- |
| `event.updated_at` | **설계 7.2.1의 좀비 회수 쿼리가 `updated_at` 을 쓰는데 7.1 스키마에 그 컬럼이 없다.** 문서 내부의 불일치다 |
| `event.last_backoff_ms` | decorrelated jitter 는 `random(initial, prev * 3)` 이라 직전 대기 시간을 알아야 한다. 어디에도 저장할 곳이 없었다 |
| `event.content_type` | 전달할 때 원본 `Content-Type` 을 복원해야 한다. 헤더 JSON 에서 꺼내도 되지만 자주 읽는 값이라 컬럼으로 뺐다 |
| `delivery_attempt.outcome` | 시도 결과가 `DELIVERED`/`RETRY`/`DEAD` 중 무엇이었는지. 응답 코드만으로 역추론하면 커넥션 거부(코드 없음)와 판정 규칙 변경 이력을 구분할 수 없다 |

`event.status` 에서는 설계 7.2.2에 따라 `FAILED` 를 뺐다.

### 5.2 attempt_count 를 클레임 시점에 증가시킨다

전달 완료 시점이 아니라 **집는 순간** 올린다.

이렇게 하면 좀비가 시도 한 번을 소진한다. 프로세스가 죽어 회수된 건은 이미 소비자에게 도달했을 수도
있으므로(설계 7.2.1), 공짜로 무한히 재시도하게 두면 안 된다. 대신 최대 시도 횟수는
"성공한 시도"가 아니라 "시작한 시도"의 상한이 된다.

### 5.3 헤더는 화이트리스트가 아니라 최소 블록리스트로 거른다

`HeaderPolicy` 는 hop-by-hop 헤더, 다음 홉에서 새로 계산될 헤더(`Host`, `Content-Length`),
자격 증명(`Authorization`, `Cookie`)만 뺀다.

화이트리스트를 쓸 수 없는 이유는 **무엇이 서명 헤더인지 제공자마다 다르고 미리 다 알 수 없기 때문**이다.
`PASSTHROUGH` 모드는 소비자가 원 제공자의 서명을 재검증하는 것이 전제인데(설계 9.5),
모르는 제공자의 서명 헤더를 실수로 떨어뜨리면 소비자 쪽 검증이 조용히 깨진다.

자격 증명을 빼는 것은 별개 이유다. 원장은 `retention_days` 동안 남으므로 애초에 담지 않는다.

### 5.4 워커는 고정 스레드풀이다

Java 21 이므로 가상 스레드를 쓸 수 있지만 쓰지 않았다.

무제한으로 띄우면 **소비자가 느려질 때 게이트웨이가 소비자를 더 세게 때린다.**
워커 수가 곧 소비자에 대한 동시 요청 상한이어야 한다. 같은 이유로 폴링은 `fixedDelay` 이고
한 배치가 전부 끝난 뒤에 다음 사이클을 돈다 — 인플라이트가 `batch-size` 를 넘지 않는다.

서킷 브레이커(설계 8.3)가 들어오기 전까지는 이것이 유일한 압력 제어다.

### 5.5 기타

| 결정 | 근거 |
| --- | --- |
| 리다이렉트를 따라가지 않는다 | 소비자 엔드포인트는 고정 주소여야 한다. 따라가면 웹훅 원본이 의도치 않은 곳으로 흘러갈 수 있다 |
| 401 응답에 실패 사유를 담지 않는다 | 어디가 틀렸는지 알려주면 공격자에게 힌트가 된다. 사유는 로그에만 남긴다 |
| `Clock` 을 빈으로 둔다 | 테스트 때문만이 아니다. 타임스탬프 윈도우가 서버 시계에 의존하므로(설계 13절 "시계 오차") 시간 출처를 한 곳으로 모은다 |
| 관리 API 토큰이 비면 필터를 등록하지 않는다 | 로컬 검증 환경에서 토큰을 요구하면 설계 11절의 반복 실험이 번거로워진다. 운영에서는 반드시 설정한다 |
| 다중 값 헤더는 첫 값만 저장 | 서명 헤더가 여러 개인 제공자는 아직 없다. 필요해지면 JSON 컬럼 구조를 배열로 바꾼다 |

## 6. 환경 관련 처리

작업 환경에서 걸렸던 것들이다. 다른 사람이 같은 곳에서 막힐 수 있어 남긴다.

| 문제 | 처리 |
| --- | --- |
| Gradle 미설치 | wrapper 를 부트스트랩해서 커밋했다. `./gradlew` 만으로 빌드된다 |
| Docker Engine 29 가 Testcontainers 를 거부 | 엔진이 API 1.40 미만 요청을 400 으로 떨군다. Testcontainers 가 쓰는 docker-java 의 기본 협상 버전이 그보다 낮다. `build.gradle` 의 test 태스크에서 `api.version=1.44` 를 명시했다. `-Dapi.version=` 으로 덮어쓸 수 있다 |
| 컨테이너를 클래스마다 껐다 켜면 커넥션 풀이 죽은 포트를 붙든다 | `@Testcontainers`/`@Container` 대신 싱글턴 컨테이너를 쓴다. Spring 의 컨텍스트 캐시와 수명을 맞추기 위해서다 |
