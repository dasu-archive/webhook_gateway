## 0. v1 범위 체크리스트

설계 12.1이 열거한 v1 포함 항목 기준이다.

| | 항목 | 상태 |
| --- | --- | --- |
| ✅ | 엔드포인트 등록 및 시크릿 관리(로테이션 포함) | 완료 |
| ✅ | 제공자 2종 서명 검증 | 완료 (`github`, `standard`) |
| ✅ | 원본 저장, 멱등키 기반 중복 차단 | 완료 |
| ✅ | 단일 목적지 전달 | 완료 |
| ✅ | 지수 백오프 + 지터 재시도, 데드레터 | 완료 |
| ✅ | 이벤트 조회 | 완료 |
| ❌ | **단건 및 범위 재생, 드라이런** | 미구현 |
| ❌ | **멱등키 정리 배치** | 미구현 |

**v1 까지 남은 기능은 둘이다.** 나머지 항목은 v1 목록 밖이거나 측정·운영 과제다.

## 1. 우선순위

| 순위 | 과제 | 왜 이 순서인가 |
| --- | --- | --- |
| 1 | 멱등키 정리 배치 | 안 하면 시간이 지날수록 반드시 나빠진다. 되돌리기가 가장 어렵다 |
| 2 | 시크릿 암호화 | 운영 데이터가 들어가기 전에 해야 한다. 나중에 하면 마이그레이션이 붙는다 |
| 3 | 데드레터 알림 | 현재 데드레터는 아무도 보지 않는 무덤이다 |
| 4 | 재생 + `resign` 모드 | FM-6 이 아직 안 막혔다. 원본은 쌓이는데 흘릴 수단이 없다 |
| 5 | 부하 측정 | 설계가 "미측정"으로 남긴 판단들이 여기서 확정된다 |
| 6 | 서킷 브레이커 | 5번의 결과가 임계값을 정해준다 |
| 7 | 실제 제공자 연결 | 폐쇄 루프에서 벗어난다 |
| 8 | 큰 페이로드 분리 | 5번의 크기별 측정 결과가 임계값을 정해준다 |

## 2. 지금 하지 않으면 나빠지는 것

### 2.1 멱등키 정리 배치 — 최우선

설계 7.5, 13절.

| | |
| --- | --- |
| **현재 상태** | `endpoint.retention_days` 컬럼은 있고 기본값 7이다. **삭제하는 코드가 없다** |
| **언제 문제가 되나** | 지금은 아니다. 몇 달 뒤 `uk_event_idem` 인덱스가 커지면서 수신 경로의 INSERT 가 느려진다 |
| **왜 위험한가** | 문제를 인지하는 시점이 이미 늦다. 그때는 지울 데이터가 이미 많고, 대량 DELETE 자체가 부하가 된다 |

설계 문서가 이렇게 적었다.

> 정리 배치를 v1에 포함한다. **나중에 붙이면 이미 문제가 된 뒤다.**

해야 할 것:

- `retention_days` 를 지난 `DELIVERED` 이벤트를 지우는 배치. `@Scheduled` 일 주기
- **`DEAD` 는 함께 지우면 안 된다.** 데드레터는 사람이 보고 판단해야 하는 것이고,
  보관 기간의 목적(제공자 재시도 윈도우)과 성격이 다르다. 별도 정책이 필요하다
- `delivery_attempt` 가 FK 로 걸려 있으므로 먼저 지운다
- 한 번에 다 지우지 말고 `LIMIT` 을 걸어 나눠 지운다. 큰 DELETE 는 락을 오래 잡는다

### 2.2 시크릿이 평문으로 저장된다

| | |
| --- | --- |
| **현재 상태** | `endpoint.secret_current VARBINARY(255)` 에 원문 바이트가 그대로 들어간다 |
| **언제 문제가 되나** | DB 덤프나 백업이 유출되는 순간. 시크릿을 알면 **누구나 가짜 웹훅을 보낼 수 있다** |
| **왜 지금 해야 하나** | 운영 시크릿이 들어간 뒤에 바꾸면 재암호화 마이그레이션이 붙는다 |

설계 문서가 이 항목을 다루지 않았다. 서명 검증을 자세히 다루면서 정작 그 키의 보관은 빠져 있다.

해야 할 것:

- 최소한 애플리케이션 레벨 대칭키 암호화. 키는 환경변수나 시크릿 매니저에서 주입
- 관리 API 응답에 시크릿이 실리지 않는 것은 이미 지켜지고 있다(`EndpointView` 에 필드가 없다)
- 로그에도 실리지 않는지 확인

### 2.3 데드레터가 무덤이다

설계 8.5, 13절.

| | |
| --- | --- |
| **현재 상태** | `DEAD` 전환 시 `log.error` 한 줄. `GET /admin/stats` 로 건수는 볼 수 있다 |
| **문제** | **알림이 없으면 아무도 안 본다.** 설계가 함정으로 명시한 항목이다 |

설계는 "데드레터 진입 자체가 알림 이벤트여야 한다"고 적었다. 로그는 알림이 아니다.

해야 할 것: 최소한 로그 레벨 알림 연동(Slack 웹훅 등)이나 메트릭 카운터 + 임계값 알림.
`management.endpoints` 에 actuator 가 이미 열려 있으므로 Micrometer 카운터가 가장 싸다.

## 3. v1 기능으로 남은 것

### 3.1 재생 (설계 9절)

FM-6 — 소비 로직 버그를 고친 뒤 과거 이벤트를 다시 흘리는 것 — 이 아직 안 막혔다.
**원본은 쌓이고 있는데 흘릴 수단이 없다.**

이미 깔려 있는 것:

| | |
| --- | --- |
| `event.replay_of` 컬럼 | 재생 이벤트가 원본을 가리킨다 |
| `X-Gateway-Replay` 헤더 | 전달 시 이미 붙는다 (현재는 항상 `false`) |
| 원본 바디와 헤더 | 원장에 그대로 있다 |

해야 할 것:

- **드라이런부터** 만든다. 실제 발송 없이 대상 건수와 목적지만 계산한다.
  범위를 잘못 잡은 재생은 되돌릴 수 없다
- 범위 지정: 시간 구간, 엔드포인트, 상태
- 재생 이력 테이블: 누가 언제 어떤 범위를 재생했는지
- **재생은 소비자 멱등성을 전제로만 성립한다**(설계 9.2). 이 경계를 관리 API 응답과 문서에 명시한다.
  결제 이벤트를 재생하면 메일이 다시 나가고 재고가 또 빠진다. 게이트웨이가 막을 수 없다

### 3.2 `signature_mode: resign` (설계 9.5)

재생과 한 묶음이다. 현재는 `PASSTHROUGH` 만 있고 enum 에 값이 하나뿐이다.

`PASSTHROUGH` 로는 재생이 불가능하다. 원본 서명 헤더를 그대로 보내면 **타임스탬프 윈도우 때문에
소비자 쪽 검증이 무조건 실패한다.** 그래서 재생을 켜려면 게이트웨이가 자기 시크릿으로
재서명해야 한다.

이때 **신뢰 경계가 이동한다.** 소비자는 이제 GitHub 을 신뢰하는 것이 아니라 게이트웨이를 신뢰한다.
그래서 2.2(시크릿 암호화)가 이것보다 먼저다 — 게이트웨이의 시크릿 관리 책임이 커지기 때문이다.

전환 전략은 설계대로다. 붙일 때는 `passthrough` 로 소비자 코드를 안 건드리고 도입하고,
안정화 후 `resign` 으로 바꿔 재생을 켠다.

## 4. 설계가 "미측정"으로 남긴 것

설계 11.2의 측정 항목과 그것이 확정해줄 판단들이다.

| 측정 | 무엇이 결정되나 | 설계 근거 |
| --- | --- | --- |
| 수신 응답 지연 p50/p99 | 목표 p99 50ms 달성 여부 | 6.4 |
| 워커 수별 폴링 p99 와 락 경합 | **DB 큐 → 브로커 전환 기준** | 10.1 |
| `idx_event_dispatch` 의 실제 잠금 범위 | `SKIP LOCKED` 가 갭 락 때문에 예상보다 넓게 잠그는지 | 10.2 |
| 복구 소진 시간 | 소비자 5분 다운 후 밀린 건 소진 곡선 | 11.2 |
| 지터 3종 복구 곡선 비교 | 어느 전략을 기본값으로 둘지 | 8.2 |
| 페이로드 크기별 수신 지연 | 오브젝트 스토리지 분리 임계값 | 13 |

설계 10.2가 이렇게 적었다.

> `idx_event_dispatch (status, next_attempt_at)` 가 실제로 잠금 범위를 좁히는지 실행 계획으로
> 확인해야 한다. **이 부분은 실측 전까지 불확실하다.**

아직 불확실한 채다. 설계 14절 6번 한계("DB 큐의 처리량 상한은 미측정")도 그대로 남아 있다.

해야 할 것: k6 스크립트 작성. 목 소비자가 이미 시나리오 제어를 지원하므로 부하 도구만 있으면 된다.

## 5. v1 목록 밖이지만 예정된 것

### 5.1 서킷 브레이커 (설계 8.3)

현재 소비자에 대한 압력 제어는 **워커 스레드 수(기본 8)와 배치 크기(기본 50)뿐**이다.
소비자가 지속적으로 5xx 를 뱉는데 계속 때리면 복구를 방해한다.

4절의 측정이 임계값을 정해준다. 그전에 만들면 숫자를 감으로 정하게 된다.

### 5.2 큰 페이로드 (설계 13절)

현재 1MB 초과는 413 으로 **거부한다.** GitHub push 웹훅은 커밋이 많으면 MB 단위가 되므로
실제로 걸릴 수 있다.

설계는 임계값 이상을 오브젝트 스토리지로 분리하라고 했다. 임계값은 4절의 크기별 측정에서 나온다.

### 5.3 실제 제공자 연결

현재 검증 구성은 폐쇄 루프다. 내가 만든 발신자가 내 게이트웨이로 쏘고 내 목 소비자가 받는다.

설계 11.1이 권한 대로 **GitHub 웹훅**을 붙이는 것이 좋다. 무료이고, 재시도하지 않는 제공자라
FM-2 검증에도 적합하다. 로컬에서는 ngrok 등으로 터널링한다.

## 6. 해결이 아니라 인지해야 하는 것

설계 14절의 한계 중 **구현으로 없앨 수 없는 것들**이다. 없애려 하지 말고 문서와 소비자 가이드에
계속 남겨야 한다.

| 한계 | 왜 못 없애나 |
| --- | --- |
| exactly-once 를 제공하지 않는다 | 분산 트랜잭션 없이 불가능하다. at-least-once + 소비자 멱등성이 유일한 실용적 해법이다 |
| 순서를 보장하지 않는다 | 설계 12.2의 의도적 제외다. 비용 대비 효용이 낮다. 소비자가 이벤트 시각으로 판정해야 한다 |
| 제공자 이벤트 ID 가 없으면 멱등성이 근사치다 | 바디 해시는 같은 사용자의 정상 중복 액션을 오판할 수 있다. `idempotency_source` 로 구분만 해둔다 |
| 재생은 소비자 멱등성 없이 안전하지 않다 | 부작용을 게이트웨이 단독으로 막을 수 없다 |

### 그리고 하나 더 — 게이트웨이 자신이 단일 장애점이다

설계 14절 7번이다. 이건 인지만으로 끝나지 않고 **가용성 설계가 필요한 항목**이다.

> FM-2 를 풀려고 만든 물건이 같은 문제를 자기 자신에게 갖는다.

도입 전에는 제공자와 소비자가 직결이라 중간이 없었다. 이제 게이트웨이가 죽으면,
재시도하는 제공자(PG사)는 흡수되지만 **재시도하지 않는 제공자(GitHub)에게 온 것은 유실된다.**

게이트웨이의 가용성 요구사항이 소비자보다 높다. 최소한 다중화와 무중단 배포가 전제되어야 하는데,
전달부가 `SKIP LOCKED` 로 이미 다중 워커를 견디도록 만들어져 있으므로
**수평 확장 자체는 지금 구조에서 가능하다.** 검증은 4절의 폴링 부하 측정과 함께 해야 한다.

## 7. 요약

```
v1 까지:        재생(드라이런 우선) + 멱등키 정리 배치
운영 전 필수:    시크릿 암호화, 데드레터 알림
그다음:          부하 측정 → 서킷 브레이커 → 큰 페이로드 분리
계속 남는 것:    at-least-once, 순서 미보장, 게이트웨이 SPOF
```

가장 먼저 할 것은 **멱등키 정리 배치**다. 기능이 아니라서 눈에 안 띄지만,
설계 문서가 유일하게 "나중에 붙이면 이미 문제가 된 뒤"라고 못 박은 항목이다.
