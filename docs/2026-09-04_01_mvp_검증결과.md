## 1. 검증 환경

설계 11.1이 말한 대로 **제공자와 소비자를 전부 직접 만들었다.** 실제 제공자로는
소비자를 죽였다 살리는 상황을 만들 수 없다.

| 구성 | 정체 | 위치 |
| --- | --- | --- |
| 제공자 | 서명 붙여 POST 쏘는 셸 스크립트 | `tools/send.sh` |
| 게이트웨이 | 결과물 | `./gradlew bootRun` |
| DB | MySQL 8.0 컨테이너 | `compose.yaml` (`localhost:3307`) |
| 소비자 | 시나리오 제어 가능한 목 서버 | `tools/MockConsumer.java` |

목 소비자가 할 수 있는 것: 항상 2xx / 항상 5xx / 4xx / N초 지연 / 처음 M회 실패 후 성공 /
N초간 다운 / **받은 이벤트 ID 별 수신 횟수 기록**.

마지막 항목이 핵심이다. 이것이 없으면 "중복 0건"을 증명할 수 없다.

**이 구성은 폐쇄 루프다.** 내가 만든 발신자가 내 게이트웨이로 쏘고 내 목 소비자가 받는다.
실제 제공자(GitHub) 연결은 아직 하지 않았다 — 남은 과제 문서 참고.

## 2. 자동화 테스트

```
./gradlew test  →  31 tests, BUILD SUCCESSFUL in 22s
```

| 클래스 | 개수 | 종류 | 무엇을 지키는가 |
| --- | --- | --- | --- |
| `SignatureVerifierTest` | 8 | 단위 | 서명 검증의 세 논점 (설계 6.2) |
| `BackoffCalculatorTest` | 5 | 단위 | 백오프와 지터 3종 (설계 8.2) |
| `ReceiveIntegrationTest` | 8 | MySQL 통합 | 원본 보존과 중복 차단 (설계 6, 7.4) |
| `DispatchIntegrationTest` | 10 | MySQL 통합 | 전달 판정과 좀비 회수 (설계 8, 7.2.1) |

통합 테스트는 H2 로 대체할 수 없다. **검증 대상 자체가 MySQL 기능**이기 때문이다 —
`FOR UPDATE SKIP LOCKED`(8.0 전용)와 유니크 인덱스 기반 중복 차단.

### 특히 중요한 테스트 셋

| 테스트 | 이것이 깨지면 |
| --- | --- |
| 바디가 1바이트만 달라도 서명이 깨진다 | 원본 보존(P2)이 무너진 것이다. 재직렬화한 바디로는 검증이 원천적으로 불가능하다 |
| 동시에 같은 이벤트가 쏟아져도 정확히 한 건만 저장된다 | 조회 후 삽입으로 되돌아간 것이다. 16스레드 동시 주입에서 `accepted=1, duplicate=15` 를 확인한다 |
| 구 시크릿으로 서명된 재시도도 유예 기간에는 통과한다 | 시크릿 로테이션이 불가능해진다. 교체 순간 날아오던 재시도가 전부 401 이 된다 |
| 오래된 타임스탬프는 거부한다 | 재전송 공격이 열린다. 가로챈 유효 요청을 나중에 그대로 보내도 통과한다 |
| `claimBatch` 로 집은 건은 다른 워커가 다시 집지 못한다 | 워커를 늘리면 중복 전달이 배가된다 |
| `DELIVERING` 인 채 죽은 행을 좀비 회수가 되돌린다 | 프로세스가 죽을 때마다 이벤트가 영구히 멈춘다. 폴링은 `PENDING` 만 본다 |
| 4xx 는 즉시 DEAD, 429 는 재시도 | 판정 규칙이 뒤집히면 이벤트를 잃거나 소비자를 계속 때린다 |

## 3. 실측 시나리오

목 소비자와 발신 스크립트로 실제로 띄워서 돌렸다. 아래는 실행 결과 그대로다.

### 3.1 정상 경로

```
등록:  POST /admin/endpoints  → id=1, slug=gh-push, target=localhost:9090/consume
발사:  tools/send.sh gh-push topsecret-secret-1234 github
       → HTTP 200 {"eventId":1,"status":"accepted"}
원장:  status=DELIVERED  attemptCount=1  idempotencySource=PROVIDER_ID
       receivedAt 06:23:27.869 → updatedAt 06:23:28.271   (402ms)
소비자: totalRequests=1  delivered=1  duplicates=0
```

수신에서 전달 완료까지 402ms. 대부분이 폴링 대기(최대 500ms)다.
**수신 응답 자체는 이와 무관하다** — 제공자는 이미 200 을 받고 끊었다.

### 3.2 중복 차단 (설계 7.4)

같은 이벤트 ID 로 20건을 연속 발사했다.

```
발신 결과:  accepted=1  duplicate=19  기타=0  (총 20)
소비자 상태: totalRequests=2  distinctEvents=2  duplicates=0
```

**소비자에게 간 것은 1건이다.** 유니크 인덱스가 나머지 19건을 삽입 단계에서 떨궜고,
제공자에게는 200 을 돌려줘 재시도를 멈추게 했다.

> 관찰: 이벤트 ID 가 `2` 다음 `22` 로 뛴다. InnoDB 는 유니크 위반으로 실패한 INSERT 에서도
> auto_increment 를 소비한다. 동작상 문제는 없지만 이벤트 ID 를 연속된 수로 가정하면 안 된다.

### 3.3 재시도와 백오프 (설계 8.2)

목 소비자를 "처음 3회는 503, 그 다음부터 200"으로 설정했다. 지터는 기본값 `FULL`.

| 시도 | 시각 | 응답 | 결과 | 직전 시도와의 간격 |
| --- | --- | --- | --- | --- |
| 1 | 06:23:44.799 | 503 | RETRY | — |
| 2 | 06:23:45.334 | 503 | RETRY | 535ms |
| 3 | 06:23:47.417 | 503 | RETRY | 2,083ms |
| 4 | 06:23:49.496 | **200** | **DELIVERED** | 2,079ms |

최종: `status=DELIVERED  attemptCount=4  lastBackoffMs=1972`

지수 백오프의 base 는 1s → 2s → 4s 로 자라고, `FULL` 지터가 각 구간에서 `random(0, base)` 를
뽑는다. **간격이 base 를 그대로 따라가지 않고 흩어지는 것**이 지터가 작동한 증거다.

간격이 백오프보다 조금씩 큰 이유는 폴링 지연이다. 3번째 구간에서 확인된다.

```
lastBackoffMs = 1972 (계산된 대기)
관측 간격     = 2079ms
차이          =  107ms  ← 폴링 주기(500ms) 안에서 집힐 때까지 기다린 시간
```

이 폴링 지연은 설계 10.1이 DB 큐의 단점으로 적어둔 그 항목이다.

### 3.4 4xx 는 즉시 DEAD (설계 8.1.1)

```
목 소비자 모드: FAIL_4XX (400 반환)
결과: status=DEAD  attemptCount=1
```

엔드포인트의 `maxAttempts` 가 8인데도 **한 번 만에 끝났다.** 재시도해도 결과가 같기 때문이다.

이 시점 원장 통계: `{"PENDING":0, "DELIVERING":0, "DELIVERED":3, "DEAD":1}`

### 3.5 제공자 2종

```
github    → event 1, 22, 23   X-Hub-Signature-256 + X-GitHub-Delivery
standard  → event 24          webhook-id/timestamp/signature, DELIVERED, PROVIDER_ID
```

두 형식 모두 서명 검증을 통과하고 동일한 원장·전달 경로를 탄다.

### 3.6 거부 경로

| 요청 | 응답 |
| --- | --- |
| 위조 서명 (`sha256=00000000`) | **401** |
| 없는 엔드포인트 (`/webhooks/nope`) | **404** |

401 응답 본문에는 실패 사유가 없다. 사유는 게이트웨이 로그에만 남는다.

## 4. 아직 측정하지 않은 것

설계 11.2의 측정 항목 중 이번에 다루지 못한 것들이다.

| 항목 | 상태 | 왜 필요한가 |
| --- | --- | --- |
| 수신 응답 지연 p50/p99 | **미측정** | 목표가 p99 50ms 인데 숫자가 없다. 부하 도구가 있어야 한다 |
| 복구 소진 시간 | **미측정** | 소비자 5분 다운 후 밀린 건이 언제 소진되는지. 곡선을 기록해야 한다 |
| 지터 효과 비교 | **구현만** | 3종을 다 만들었으나 복구 곡선을 그려 비교하지 않았다. 설계가 요구한 그래프가 없다 |
| 중복 차단 | **측정 완료** | 위 3.2. 동시 주입은 통합 테스트로도 확인 |
| 페이로드 크기 영향 | **미측정** | 1KB/100KB/1MB 수신 지연. 설계 13절의 임계값을 정할 근거다 |
| 큐 폴링 부하 | **미측정** | 워커 수별 폴링 p99 와 락 경합. **설계 10.1의 DB 큐 → 브로커 전환 기준이 여기서 나온다** |

마지막 항목이 특히 중요하다. 설계 10.2는 `SKIP LOCKED` 를 걸어도 갭 락 때문에 예상보다 넓은
범위가 잠길 수 있다며 **"이 부분은 실측 전까지 불확실하다"**고 적었다. 아직 불확실한 채다.

## 5. 결론

**설계가 세운 실패 모드 FM-1 ~ FM-6 중 이번에 실제로 막힌 것:**

| | 무엇이 막았나 | 확인 |
| --- | --- | --- |
| FM-1 처리 시간이 수신 응답 시간이 된다 | 수신과 전달의 시간축 분리 | 3.1 — 구조상 분리됐다. 다만 **느린 소비자를 붙인 실측은 아직 없다**(4절) |
| FM-3 정상 처리했는데 중복이 온다 | 멱등키 + 유니크 인덱스 | 3.2 — 20건 중 1건만 소비자 도달 |
| FM-5 실패한 요청의 흔적이 없다 | 원장 + `delivery_attempt` | 3.3, 3.4 — 실패 시도까지 전부 남음 |

**아직 못 막은 것:**

- **FM-2 (배포 중 유실)** 는 게이트웨이 자신에게 그대로 남아 있다. 설계 14절 7번 한계 그대로다.
- **FM-4 (순서 역전)** 는 설계 12.2가 의도적으로 제외했다. 소비자가 이벤트 시각으로 판정해야 한다.
- **FM-6 (소비 로직 버그 되돌리기)** 는 재생 기능이 필요하다. 원본은 보존되고 있으나 다시 흘릴 수단이 없다.

## 6. 재현 방법

```bash
docker compose up -d                          # MySQL 8.0
java tools/MockConsumer.java 9090             # 목 소비자
./gradlew bootRun                             # 게이트웨이

curl -X POST localhost:8080/admin/endpoints -H 'Content-Type: application/json' \
  -d '{"slug":"gh-push","provider":"github","secret":"topsecret-secret-1234",
       "targetUrl":"http://localhost:9090/consume","maxAttempts":8}'

tools/send.sh gh-push topsecret-secret-1234 github            # 정상
tools/send.sh gh-push topsecret-secret-1234 github - 20 --same-id   # 중복
curl -X POST 'localhost:9090/_control/mode?mode=FAIL_THEN_OK&failFirst=3&status=503'
curl -X POST 'localhost:9090/_control/down?seconds=60'        # 소비자 다운
```

각 시나리오의 자세한 절차는 [README](../README.md#검증-시나리오) 참고.
